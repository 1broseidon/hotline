# OS passkeys: can the desk ask the OS for a passkey for any site?

Spike for task-269 (epic-24), 2026-10-22. Feeds the decision on task-270.

**Answer for task-270: no, not as scoped.** macOS comes first (epic-24 decision 12), and on macOS the only public route is an entitlement Apple grants to web browsers. Hotline does not meet Apple's written test for a browser. Windows can do it today with no permission from anyone. Linux has no API for it. The answer becomes yes for macOS only if Apple grants the entitlement (see section 5).

Confidence tags: **[high]** means docs or source code say it directly. **[med]** means it follows from the docs but nothing states it outright. **[low]** means inference, or community reports only.

## 0. What the relay has to work with

- The container's extension attaches with `chrome.webAuthenticationProxy`. It receives `requestDetailsJson` (the `get()`/`create()` options as JSON) and must answer with `responseJson` (a `PublicKeyCredential.toJSON()`, which includes `clientDataJSON`). <https://developer.chrome.com/docs/extensions/reference/api/webAuthenticationProxy> **[high]**
- The page's real origin is in that JSON. Before proxying, Chromium writes `extensions.remoteDesktopClientOverride = {origin: caller_origin, sameOriginWithAncestors}` into the options ([authenticator_common_impl.cc](https://source.chromium.org/chromium/chromium/src/+/main:content/browser/webauth/authenticator_common_impl.cc), the `GetWebAuthnRequestProxyIfActive` branches; serialized in [value_conversions.cc](https://source.chromium.org/chromium/chromium/src/+/main:components/webauthn/json/value_conversions.cc)). **[high]**
- **Conditional (autofill) `get()` calls are refused with NotAllowedError while a proxy is attached** (same file: `options->mediation == Mediation::CONDITIONAL`). Sites have to use their "Sign in with a passkey" button flow. **[high]**
- So the host OS must either sign over a `clientDataJSON` we supply (Windows), or build one from a challenge and origin we supply and hand it back (Apple). Either way works.

## 1. macOS

**Without the entitlement it cannot work.** `ASAuthorizationPlatformPublicKeyCredentialProvider(relyingPartyIdentifier:)` only works for domains in the app's Associated Domains `webcredentials:` list, and each domain must serve an `apple-app-site-association` file naming the app ([Apple sample, setup steps 4–5](https://developer.apple.com/documentation/authenticationservices/connecting-to-a-service-with-passkeys)). github.com will never list Hotline. **[high]**

**The entitlement.** [`com.apple.developer.web-browser.public-key-credential`](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.web-browser.public-key-credential) (macOS 13.3+) "lets your app make registration and assertion requests for passkeys and security keys for any relying party identifier." Its terms **[high]**:
- "Only add this entitlement if your app can act as a user's web browser."
- The Account Holder must request it through the [macOS Browsers Passkeys form](https://developer.apple.com/contact/request/macos-browsers-passkeys/). Apple reviews it "using predefined criteria" and grants it as a managed capability. A DTS reply confirms that only the Account Holder can reach the form ([forum 829169](https://developer.apple.com/forums/thread/829169), June 2026).
- Criteria: the app declares the `http`/`https` schemes in Info.plist; on launch it offers a URL field, search, or bookmarks; and opening a URL "navigate[s] directly to the specified destination and render[s] the expected web content."
- Nothing in the docs requires the app to be the default browser or to ship through the App Store. A non-App Store wrapper app asked in the forum thread above and DTS did not object. **[med]**
- **Hotline's fit: poor.** Hotline does not handle http/https links or render sites. A URL field added only to qualify would break our no-fake-UI rule and would likely fail review anyway. **[low; Apple's judgement]**

**Setting the client data: solved by public API.** [`ASPublicKeyCredentialClientData`](https://developer.apple.com/documentation/authenticationservices/aspublickeycredentialclientdata-swift.struct) (macOS 13.5+) has `initWithChallenge:origin:`, `topOrigin` and `crossOrigin`. It is passed to the [`ASAuthorizationWebBrowserPlatformPublicKeyCredentialProvider`](https://developer.apple.com/documentation/authenticationservices/asauthorizationwebbrowserplatformpublickeycredentialprovider-19bq) methods `createCredentialAssertionRequest(clientData:)` and `createCredentialRegistrationRequest(clientData:name:userID:)`, which `ASAuthorizationPlatformPublicKeyCredentialProvider` conforms to (confirmed in the macOS 27 SDK headers). **[high]**
- The origin can be the remote page's origin (`https://github.com`); that is what the API is for. The OS builds `clientDataJSON` and returns it as `rawClientDataJSON` on the credential. We relay those exact bytes. We cannot pass in a precomputed hash. **[high]**
- Chrome passes `clientDataHash` through private AuthenticationServicesCore SPI ([icloud_keychain_internals.h](https://source.chromium.org/chromium/chromium/src/+/main:device/fido/mac/icloud_keychain_internals.h)). We don't need that and shouldn't use it.
- Security keys use the same entitlement through `ASAuthorizationWebBrowserSecurityKeyPublicKeyCredentialProvider` (macOS 14.4+). That reaches USB/NFC keys, not passkey providers. **[high]**

**Third-party providers.** The browser API describes passkeys "stored in the keychain, or managed by a third-party credential manager", with a `providerName` field ([ASAuthorizationWebBrowserPlatformPublicKeyCredential](https://developer.apple.com/documentation/authenticationservices/asauthorizationwebbrowserplatformpublickeycredential-swift.struct)). Provider extensions have received passkey requests since macOS 14 ([prepareInterface(forPasskeyRegistration:)](https://developer.apple.com/documentation/authenticationservices/ascredentialproviderviewcontroller/prepareinterface(forpasskeyregistration:))). A provider only sees `clientDataHash` (`ASPasskeyAssertionCredential` initializers in the SDK), so the origin we set flows through to it. **[med: we expect an entitled app's request to reach providers, but no doc states it]**
- Who actually answers on macOS today: iCloud Keychain/Apple Passwords. 1Password, since its native macOS AutoFill reached stable in 8.12.32 in August 2026, with passkeys ([announcement](https://www.1password.community/announcements-52/macos-autofill-is-now-available-to-everyone-25254)). **Not Bitwarden** as of 2026.1 ([user report](https://community.bitwarden.com/t/register-as-macos-password-and-passkey-provider/93723)). **[med]**
- There is also a one-time "allow this browser to use passkeys" grant: [`requestAuthorizationForPublicKeyCredentials`](https://developer.apple.com/documentation/authenticationservices/asauthorizationwebbrowserpublickeycredentialmanager), shown in System Settings under *Passkeys Access for Web Browsers* ([Langley](https://imperialviolet.org/2023/10/18/icloudkeychain.html)). **[high]**

**Can the teammate's own passkey be made there and used later?** Yes, if the app is entitled. A registration request with `clientData` saves the passkey to whichever provider the person picks in the system sheet, and later assertions find it by rpId. **[med]**

## 2. Windows 11

- **Any Win32 app can call** `WebAuthNAuthenticatorMakeCredential` / `WebAuthNAuthenticatorGetAssertion` with any rpId. There is no binding between apps and domains; it is the same API Chromium and Firefox use ([Learn: WebAuthn APIs](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/webauthn-apis), [webauthn.h](https://github.com/microsoft/webauthn/blob/master/webauthn.h)). **[high]**
- **We supply the client data.** `WEBAUTHN_CLIENT_DATA` takes `pbClientDataJSON` plus `pwszHashAlgId`, so we write the JSON with the remote origin. The public API rejects hash-only input ([Unit 42 analysis](https://unit42.paloaltonetworks.com/webauthn-added-to-browser-based-rdp/)). That doesn't matter here because the relay has the full request. API v9 adds `pwszRemoteWebOrigin` ("For Remote Web App scenario") and `pbAuthenticatorId`, which pairs with `WebAuthNGetAuthenticatorList` (webauthn.h). **[high]**
- **Third-party passkey managers.** The plugin model forwards WebAuthn calls to the provider and returns the response to the calling app ([Insider build 22635.4515](https://blogs.windows.com/windows-insider/2024/11/22/announcing-windows-11-insider-preview-build-22635-4515-beta-channel/)). It is generally available since the November 2025 update, with 1Password and Bitwarden ([heise](https://heise.de/-11075433)). It is enabled under Settings > Accounts > Passkeys > Advanced options ([Learn: plugin passkey managers](https://learn.microsoft.com/en-us/windows/apps/develop/security/third-party)). Plugins receive `pbClientDataHash` ([webauthnplugin.h](https://github.com/microsoft/webauthn/blob/master/webauthnplugin.h)). **[med-high: routing happens at OS level, but no doc names non-browser callers]**
- Making a passkey: `MakeCredential` offers the provider choice, and later `GetAssertion` calls use the same passkey. **[med]**

## 3. Linux

Not yet. [credentialsd](https://github.com/linux-credentials/credentialsd) (Credentials for Linux) is a D-Bus service with a reference UI. Its latest release is v0.3.1 (Sept 2026), still marked pre-release. A portal spec is planned, and "a uniform interface for third-party credential providers" is listed as a goal in GOALS.md. The demo extension only works on webauthn.io and demo.yubico.com ([FOSDEM 2026 talk](https://fosdem.org/2026/schedule/event/credentials-for-linux-bringing-passkeys-to-linux)). **[high]** Linux hosts keep using capture.

## 4. Alternatives

- **The person's local Chrome or Edge as the signer.** This is the AWS WorkSpaces Secure Browser design: a remote browser, with WebAuthn redirected to the user's local Chromium via `remoteDesktopClientOverride` ([AWS docs](https://docs.aws.amazon.com/workspaces-web/latest/adminguide/web-authentication.html)). The local browser has to allow our HTTPS origin in the `WebAuthenticationRemoteDesktopAllowedOrigins` policy: Chrome 136+, Edge 137+ on Windows and macOS. The policy is mandatory-only, and Edge applies it only to "affiliated users" ([Edge policy](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/webauthenticationremotedesktopallowedorigins)). It needs no Apple entitlement. The costs: the person installs a configuration profile, Chrome's own WebAuthn UI appears, and we haven't verified that Chrome on macOS reaches third-party providers. **[med]** This is the only route on macOS we can try today without asking Apple.
- **CTAP 2.2 hybrid, driven from the desk.** CTAP takes `clientDataHash`, which gives us full control of the origin, and needs no entitlement beyond Bluetooth permission. The phone's provider (iCloud, 1Password, Bitwarden, Google) answers ([CTAP 2.2 PS](https://fidoalliance.org/specs/fido-v2.2-ps-20250714/fido-client-to-authenticator-protocol-v2.2-ps-20250714.html)). [libwebauthn](https://github.com/linux-credentials/libwebauthn) (Rust) implements hybrid, but its Bluetooth layer is BlueZ (Linux) only, so macOS would need a CoreBluetooth scanner. It does not fit task-270: the approval is a QR scan plus the phone, not Touch ID, and decisions rule out a phone path. **[high on protocol, low on effort]**
- **CXF/CXP (moving passkeys into Hotline).** CXF v1.0 has been a Proposed Standard since August 2025 ([spec](https://fidoalliance.org/specs/cx/cxf-v1.0-ps-20250814.html)). On macOS 26, Apple's [`ASCredentialImportManager`](https://developer.apple.com/documentation/authenticationservices/ascredentialimportmanager) only imports into a credential provider extension that sets `SupportsCredentialExchange`. This moves the private key into our vault, which is the opposite of task-270's "no private key reaches the desk's vault." It is a migration path for the *Make a passkey* route, not for 270. **[high]**

## 5. Recommendation, proofs, risks

**Decision:** Do not build task-270 now. Have the Account Holder file the macOS Browsers Passkeys request anyway (it costs one form) and make 270 conditional on Apple's reply. If Apple says yes, 270 is feasible: the client-data API covers the origin, and providers answer. If Apple says no, the options are a macOS-only redesign via local Chrome or hybrid, or a Windows-first 270 (which reverses decision 12).

**Cheapest proofs (each under a day):**
1. *macOS gate.* A minimal Developer ID–signed, notarized Swift app calls `createCredentialAssertionRequest(clientData:)` for `webauthn.io` with origin `https://webauthn.io`. Today it should fail with a "not associated with domain" error, which is the gate this doc describes. Once the entitlement is granted, the same binary should show the system sheet with iCloud and 1Password. Paste `rawClientDataJSON`, `authenticatorData` and `signature` into a container Chromium extension's `completeGetRequest` and confirm that webauthn.io accepts them.
2. *Windows.* Call `WebAuthNAuthenticatorMakeCredential` and then `GetAssertion` from Rust (`windows` crate, `Win32_Networking_WindowsWebServices`) with handwritten client data, first through Windows Hello and then with the 1Password plugin. Relay the result the same way.
3. *Local-Chrome route.* Install a profile that sets `WebAuthenticationRemoteDesktopAllowedOrigins`, then serve a page that calls `navigator.credentials.get` with `remoteDesktopClientOverride`.

**Risks:**
- **Entitlement denial (likely).** Even if it's granted, Apple could later revoke it if Hotline isn't judged a browser.
- **Signing pipeline.** A managed capability needs an embedded Developer ID provisioning profile in the Tauri bundle, plus re-notarization. Restricted entitlements without a matching profile fail at launch. **[med]**
- **UX.** There is a one-time browser-access grant on macOS. Provider coverage is uneven (no Bitwarden on macOS). Autofill-style sign-ins fail under the proxy. When `onRequestCanceled` fires, the OS sheet must be dismissed with `ASAuthorizationController.cancel()` (macOS 13+) or `WebAuthNCancelCurrentOperation`.
- **Trust.** The desk signs for whatever origin the container reports. The OS prompt shows the rpId, so the person approves a *site*, not a page. A compromised container can get an assertion for any site the person approves. That matches 270's "the OS prompt is the approval," but it should be stated in the threat model.
