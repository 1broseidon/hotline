# v1 frame schema

[`frames-v1.schema.json`](frames-v1.schema.json) is the shared wire contract for frames-v1 payloads and additive mailbox-v1 transport controls. The Go and mobile fixture suites consume it directly and maintain implementation-side conformance assertions.

Implementations remain hand-written rather than generated. The mailbox-v1 definitions and frozen rules below are authoritative for M1 relay, M2 box, and M3 mobile work; the legacy frames-v1 definitions preserve the already-shipped baseline.

The schema enumerates canonical known frame shapes. Implementations intentionally tolerate additive unknown fields and unknown frame types, so the union is not a strict model of every input their decoders accept. The reserved non-JSON heartbeat strings are documented below but are not object-schema members.

## Evolution log

- **Mailbox-v1 contract freeze (2026-07-11; runtime implementation follows in M1–M3).** Added optional `hello.capabilities: ["mailbox-v1"]` and matching `welcome` echo; canonical decimal-string `$defs.mailboxCursor`; and `device_payload`, `mailbox_provision`, `mailbox_provisioned`, `device_send`, `mailbox_enqueue`, `mailbox_enqueued`, `mailbox_sync`, `mailbox_state`, `mailbox_item`, `mailbox_signal`, `mailbox_synced`, `mailbox_ack`, `mailbox_push_set`, and `mailbox_revoke` transport controls. Every wrapped payload has `payload_encoding: "plain-v1"` and opaque, verbatim frames-v1 text. `mailbox_error` is a separate transport control with codes `mailbox_gap`, `mailbox_unauthorized`, `mailbox_revoked`, `mailbox_cursor_ahead`, and `mailbox_full`; it is routed before the payload parser and never reaches `parseFrame`, the reducer, or the transcript. The five `mailbox-*.json` fixtures freeze these rules:
  - **F1/F3 — order and sync boundary.** Within one mailbox, M order equals J order. The box keeps one per-recipient envelope in flight, dispatches ascending J, and waits for `mailbox_enqueued` before the next. The relay delivers strictly ascending M on each socket, fully flushes the captured sync snapshot before live delivery, and deduplicates `envelope_id` across that boundary.
  - **F2 — personal audience.** Every personal-deployment journal event explicitly resolves to every owner device, and gap recovery replays all such events. A second user or thread audience is out of scope until a journal-audience field is added; mailbox routing alone must not be used to infer or filter journal visibility.
  - **F4 — deterministic dispatch identity.** Every journal-backed durable box-to-mailbox `envelope_id` is the opaque string `f(journal_seq, device_id)`, created inside the atomic journal-plus-dispatch write and never at send/retry time. `(mailbox_id, envelope_id)` is unique, so retries return the original M and create neither duplicate mail nor another push intent. Non-journal ephemeral signals and pre-journal `device_send` use independently sender-stable IDs because neither has a journal dispatch row.
  - **F5/F6 — authenticated route and identity.** `/b/<slug>/mailboxes` inherits the timing-safe `RELAY_BOT_TOKEN` bearer gate. A second bot or tenant additionally requires per-bot box credentials; the current shared token leaves isolation dependent on slug secrecy. Device identity binds to the relay-assigned `connection_id` or verified grant plus the box-authenticated `device_id`, never to a client-supplied payload field.
  - **F7 — durable grant.** A per-bot/device grant has at least 128 bits of entropy, is issued once after pairing, stored durably by the client, hash-stored and verified on every `mailbox_sync` by the relay, reusable until revoked, and removed on revocation. “Issued once” does not mean “usable once.”
  - **F8/F9 — no fallback and rollback push continuity.** A provisioned device never falls back to a broadcast raw socket, and envelope mode is required before a second device set or user shares a `BotRoom`. Rollback acceptance requires a sleeping device to retain push continuity: the box re-enables raw-path push and the app re-registers `/push-token` after persistent mailbox failure. Mailbox tables remain additive.
  - **F10 — decimal-safe M.** Every M field (`mailbox_seq`, `floor`, `head`, `after`, `through`, and `next`) is a canonical non-negative decimal JSON string. Implementations use BigInt or decimal-safe comparison end to end and never `Number(M)` or `parseInt(M)`; numeric frames-v1 J is unchanged.
  - **F11/F12 — transport recovery and coupled resets.** Mailbox errors stay outside the transcript. `mailbox_gap` retains J and invokes an inner `hello.last_seq=J`; an item at or below J is not re-applied but still advances and acknowledges M. A journal cold start clears the mailbox cursor, and `reset_required` triggers the same coupled reset.
  - **F13 — push intent durability.** Push-intent drain is at least once: delete an intent only after the Expo POST returns. Presence, socket delivery, or acknowledgement never cancels the first-insertion push intent.
- **Relay liveness and device presence.** The raw text strings `hl-ping` and `hl-pong` are reserved relay-transport heartbeat frames outside the JSON `frames-v1` union. The relay auto-answers `hl-ping`; both the box relay connector and relay-mode app use the response as inbound liveness. The relay-owned `{"t":"relay_presence","devices":N}` frame is bot-inbound control: the box parses it only on its dialed relay socket, never journals or broadcasts it, and silently ignores that type on LAN accepts. `devices: 0` makes relay-bound devices count as having zero connected clients for push eligibility; any positive count marks them present again. The mobile parser ignores `relay_presence` if it is ever exposed. See `protocol/fixtures/relay-presence.json`.
- **Relay photos and in-app artifacts.** Added `$defs.relayBlobRef`; relay-backed `send.attachments[]` entries carry `mime`, `size`, and `blob`; `fileRef.blob` supplies a relay capability alongside the existing local `/att/` URL. Added `$defs.artifactRef` and optional `msg.artifact` for one `static-html-v1` publication with fallback text. These fields are additive: direct clients continue to use `file.url`, relay clients prefer `blob.url`, and older clients render an artifact message's `text`.
- **Staged multi-photo compose (first post-contract evolution).** The `send` frame's reserved `attachment_id`/`attachment_name` scalars are replaced by an `attachments` array (`[{ id, name? }]`, up to ten) plus a parallel `cids` array. A client uploads each photo with `defer=1` (stored, no relay/echo), then sends all of them with one caption as a single `send` frame — one harness turn instead of one per photo. The server answers with one `sent` echo per attachment (each its own `u-<seq>` id and fileRef) plus a final `sent` echo for the caption, and the single `ack` gains an optional `message_id` carrying the turn's id (the last echo's id). All additions are backward compatible: a plain `send` and a non-`defer` upload are unchanged. See `protocol/fixtures/staged-photos.json`.
- **Delivery trust.** `ack` now means the inbound sink accepted the action, not merely that the WebSocket handler read it. A rejected sink call emits the existing `error` frame with `code: "delivery_failed"` and an additive `cid`; no accepted `sent`/`react` echo is journaled. Retrying the same device-scoped CID is idempotent within the server's bounded success cache.
